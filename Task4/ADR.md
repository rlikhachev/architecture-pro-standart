#### Обоснование решений

**Почему расширяем Deposit Service, а не создаём новый сервис:**
- Deposit Service уже управляет ставками (синхронизация с АБС через Kafka)
- Добавление API и генерации файлов — логичное расширение ответственности
- Минимизация количества новых компонентов и интеграций
- Команда банка уже имеет экспертизу в Java Spring Boot

**Почему REST API для системы кол-центра:**
- Система кол-центра построена на Java Spring Boot — нативная поддержка REST
- Подрядчик может потреблять API без значительных изменений
- Получение ставок в реальном времени (без задержки 24 часа)
- Возможность запроса персонализированных ставок в будущем

**Почему SFTP для партнёрского кол-центра:**
- Партнёрский кол-центра не может принимать API-вызовы (ограничение внешней системы)
- SFTP — стандартный протокол для обмена файлами между организациями
- Ежедневная генерация файла — достаточная частота для консультаций по ставкам
- Формат CSV — простой, поддерживается всеми системами

**Почему Kafka для синхронизации ставок АБС → Deposit Service:**
- Уже используется в архитектуре MVP (открытие депозитов)
- Декаплинг: АБС не зависит от наличия потребителей
- Надёжность: ставки не теряются при сбоях
- Расширяемость: другие системы могут потреблять ставки из Kafka

### **Альтернативы**

**Альтернатива 1: Прямая интеграция системы кол-центра с АБС**

Описание: Система кол-центра напрямую обращается к АБС для получения ставок.

Недостатки:
- АБС перегружена, прямые обращения от множества систем увеличивают нагрузку
- Нарушение требования избежать прямой интеграции с АБС
- Система кол-центра — платформа подрядчика, прямая интеграция с АБС требует доработки подрядчика
- Нет промежуточного слоя для бизнес-логики (персонализация ставок)

**Альтернатива 2: Передача ставок через АБС (без Kafka)**

Описание: АБС передаёт ставки в Deposit Service через SQL-запросы по расписанию (cron).

Недостатки:
- Задержка синхронизации — ставки могут быть неактуальны
- Нет механизма событийного взаимодействия
- Прямые SQL-запросы к Oracle нагружают АБС
- Не соответствует требованию использовать Kafka на перспективу

**Альтернатива 3: Хранение ставок в системе кол-центра**

Описание: Система кол-центра хранит копию ставок, синхронизация через API Deposit Service по расписанию.

Недостатки:
- Дублирование данных — нарушение принципа единого источника истины (single source of truth)
- При несоответствии ставок оператор может назвать клиенту устаревшую ставку
- Дополнительная нагрузка на систему кол-центра

**Альтернатива 4: Email-рассылка ставок партнёрскому кол-центру**

Описание: Deposit Service отправляет файл ставок на email партнёрского кол-центра.

Недостатки:
- Ручной процесс загрузки файла операторами партнёрского кол-центра
- Риск потери или задержки письма
- Нет автоматической интеграции с системой партнёрского кол-центра
- Ненадёжно для критичного бизнес-процесса
