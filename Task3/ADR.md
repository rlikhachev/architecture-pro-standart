#### Обоснование решений

**Deposit Service:**
- Интернет-банк интегрирован с АБС напрямую через БД. Это создаёт нагрузку на АБС и не позволяет масштабировать процесс открытия депозитов.
- Deposit Service выступает антикоррупционным слоем: изолирует клиентские каналы от внутренней логики АБС.
- Позволяет реализовать SMS-уведомления без доработки ядра интернет-банка подрядчиком.

**Kafka:**
- Декаплинг: интернет-банк не ждёт ответа от АБС напрямую (норма для очередей).
- Надёжность: сообщения не теряются при сбоях.
- Масштабирование: позволяет горизонтально масштабировать обработку заявок.
- На перспективу: банк планирует использовать Kafka для других процессов.
- Текущая платформа ИБ несовместима с Kafka — но Deposit Service на Java Spring Boot поддерживает его нативно.

**PostgreSQL:**
- Уже используется в банке (система кол-центра, кредитный скоринг).
- Есть экспертиза в команде.
- Подходит для хранения ставок, заявок и статусов.

**SMS-подтверждение через ядро ИБ:**
- Функционал SMS уже реализован в ядре интернет-банка.
- Доработка ядра подрядчиком нежелательна, но базовый механизм уже работает.
- Альтернатива (реализация в Deposit Service) потребовала бы дублирования логики.

### **Альтернативы**


**Альтернатива 1: Прямая интеграция ИБ с АБС через REST API**

Описание: Интернет-банк напрямую вызывает API АБС для получения ставок и передачи заявок.

Недостатки:
- АБС перегружена, прямые обращения от множества клиентов могут нарушить работоспособность банка.
- АБС масштабируется только вертикально — не выдержит роста нагрузки.
- Нарушается требование избежать прямой интеграции ИБ с АБС.
- Нет возможности реализовать промежуточную логику (персонализация ставок, SMS-уведомления).

**Альтернатива 2: Хранение ставок в отдельной БД (без Kafka)**

Описание: Deposit Service хранит ставки в своей БД, синхронизация с АБС происходит по расписанию (cron) через SQL-запросы к Oracle.

Недостатки:
- Задержка синхронизации — ставки могут быть неактуальны.
- Нет механизма событийного взаимодействия для уведомлений о подтверждении заявок.
- Сложнее масштабировать — прямые SQL-запросы к Oracle нагружают АБС.
- Не соответствует требованию использовать Kafka на перспективу.

**Альтернатива 3: Вынос SMS-функционала в Deposit Service полностью**

Описание: Deposit Service реализует собственную логику SMS-подтверждения, минуя ядро интернет-банка.

Недостатки:
- Дублирование логики SMS, уже реализованной в ядре ИБ.
- Дополнительные затраты на разработку и поддержку.
- Необходимость интеграции с SMS-шлюзом (уже настроена в ИБ).
